## Round 1 — Fundamentals (screening)

<details>
<summary>**1. What is MongoDB and when would you choose it over a relational database?**</summary>

MongoDB is a document database: it stores data as BSON documents — self-describing, typed, nestable — rather than as rows in fixed-schema tables. The core design principle is that data accessed together is stored together, so what would be a five-table join in Postgres is often a single document fetch.

I'd choose it when the access patterns are document-shaped and known up front: a product catalogue with wildly varying attributes per category, a content or event system where the schema evolves constantly, or anything where the natural aggregate — an order with its line items — is read and written as one unit. It also gives horizontal write scaling through sharding, which relational systems don't offer natively.

I'd choose Postgres when the workload is genuinely relational — many-to-many relationships queried from every direction, ad-hoc analytical queries whose shape I can't predict, or hard multi-table transactional integrity as a routine requirement rather than an exception. "Which is better" isn't a real question; "which access patterns do you have" is.

📖 [Document Model](./01-document-model.md)
</details>

<details>
<summary>**2. Is MongoDB schemaless?**</summary>

No — it has a *flexible* or *dynamic* schema. Every document has a structure; MongoDB just doesn't require every document in a collection to share it, and doesn't make you declare it up front. In practice the schema moves from the database into the application.

You can also enforce it server-side with `$jsonSchema` validators, and production collections should. The useful nuance is `validationLevel: "moderate"` with `validationAction: "warn"` — that's how you retrofit a schema onto a live collection without breaking existing documents.

📖 [Document Model §7](./01-document-model.md)
</details>

<details>
<summary>**3. What's the difference between BSON and JSON?**</summary>

BSON is a binary serialisation of JSON-like documents with three additions a database needs. First, **types**: JSON has one number type, while BSON distinguishes int32, int64, double, Decimal128, plus dates, binary data, and ObjectId. Second, **length prefixes**: every document and sub-document is size-prefixed, so the engine can skip over a large nested array by advancing a pointer instead of parsing it. Third, **round-trip fidelity** — a date stays a date rather than becoming a string.

The trade-off is that BSON is often slightly larger than the equivalent JSON. It spends bytes to buy traversal speed and type safety.

📖 [Document Model §2](./01-document-model.md)
</details>

<details>
<summary>**4. What is an ObjectId?**</summary>

A 12-byte identifier: a 4-byte Unix timestamp in seconds, 5 bytes of per-process randomness identifying machine and process, and a 3-byte incrementing counter. It's generated by the *driver*, not the server, which means inserts don't need a round trip to allocate an ID and thousands of application servers can generate IDs concurrently without coordination — that's why MongoDB has no auto-increment.

Because it's timestamp-prefixed, sorting by `_id` approximates sorting by creation time and you can extract the creation timestamp for free. The flip side is that it's monotonically increasing, which makes it a poor shard key.

The bug everyone hits once: an ObjectId is not the 24-character hex string you see in Compass. Querying `{ _id: req.params.id }` with a string silently returns nothing, because the BSON types don't match. You need `new ObjectId(id)`.

📖 [Document Model §3](./01-document-model.md)
</details>

<details>
<summary>**5. `{ a: null }` vs `{ a: { $exists: false } }`?**</summary>

`{ a: null }` matches documents where `a` is explicitly null **and** documents where `a` is absent entirely — that surprises people. `{ a: { $exists: false } }` matches only the absent case, and `{ a: { $type: "null" } }` matches only the explicit null.

It matters more than it sounds: "count users with no email address" gives three different numbers depending on which you pick, and only one of them answers the question you were asked.

📖 [Document Model §4](./01-document-model.md)
</details>

## Round 2 — Querying & Indexes

<details>
<summary>**6. Explain the ESR rule.**</summary>

It's the rule for ordering fields in a compound index: **Equality, then Sort, then Range**.

Equality predicates pin the leading keys to a single value, which makes everything below that point a contiguous region of the index that's already ordered by the next key. So a sort key placed immediately after the equality fields can be read straight off the index with no in-memory sort. A range predicate spans many values of its key, which interleaves the ordering of every field after it — so ranges must come last.

For `find({ status: "PAID", amount: { $gte: 500 } }).sort({ createdAt: -1 })`, the right index is `{ status: 1, createdAt: -1, amount: 1 }`. Put `amount` before `createdAt` and the explain plan grows a blocking `SORT` stage.

📖 [Indexes §3](./04-indexes-and-performance.md)
</details>

<details>
<summary>**7. A query is slow. Walk me through debugging it.**</summary>

I'd run `explain("executionStats")` and compare three numbers: `nReturned`, `totalKeysExamined`, and `totalDocsExamined`. Ideally all three are close.

If keys examined is zero and docs examined is huge, there's no usable index — a `COLLSCAN` — so I'd add one for that query shape. If keys examined vastly exceeds documents returned, an index exists but isn't selective; usually the leading field is low-cardinality, and I'd reorder it per ESR. A `SORT` stage means no index provides the requested order, which is the same fix. If docs examined greatly exceeds keys examined, there's an unindexed predicate being applied after the fetch, or multikey expansion.

If all three numbers are healthy and it's still slow, it isn't a query-plan problem. Then I'd look at whether the working set still fits in the WiredTiger cache — page faults and cache hit ratio — at document size and network transfer, and at connection pool saturation.

📖 [Indexes §4 and §7](./04-indexes-and-performance.md), [Production Playbook §5](./14-production-playbook.md)
</details>

<details>
<summary>**8. What is a covered query?**</summary>

One where every field the query touches — both the filter and the projection — exists in the index, so the plan never fetches the document. `totalDocsExamined` is zero and the stage shows `PROJECTION_COVERED`.

It needs `_id` explicitly excluded unless `_id` is part of the index, and it doesn't work on multikey indexes because the index entry doesn't record the whole array. It's often an order of magnitude faster because the index is compact and usually cache-resident — good for autocomplete, existence checks, and ID lists.

📖 [Indexes §5](./04-indexes-and-performance.md)
</details>

<details>
<summary>**9. When would you NOT add an index?**</summary>

Several cases. On a low-cardinality field on its own — an index on a boolean where 95 % of documents are `true` reads most of the collection *plus* the index, so it's slower than a scan. On small collections, where a cached scan beats the overhead. On write-heavy, rarely-queried collections like audit logs, since every index taxes every write. And any redundant prefix — `{ a: 1 }` is dead weight if `{ a: 1, b: 1 }` exists.

The operational version: run `$indexStats` and drop anything with zero accesses after a full business cycle. Indexes also consume RAM that competes with your working set, so a dead index isn't neutral — it's actively harmful.

📖 [Indexes §6](./04-indexes-and-performance.md)
</details>

<details>
<summary>**10. `$elemMatch` — why does it exist?**</summary>

Because without it, each condition on an array field is evaluated against the array independently. Given `scores: [70, 92]`, the query `{ scores: { $gt: 80, $lt: 90 } }` matches — 92 satisfies the first condition and 70 the second — even though no single element satisfies both. That's almost never the intent.

`$elemMatch` requires that **one** element satisfies all conditions. The rule of thumb is: two or more conditions on the same array means you need `$elemMatch`.

📖 [Operators — Array query operators](./07-operators-reference.md)
</details>

## Round 3 — Aggregation

<details>
<summary>**11. Explain the aggregation pipeline.**</summary>

It's an ordered sequence of stages where each stage transforms a stream of documents and passes its output to the next — essentially a Unix pipe for BSON. Most stages stream one document at a time, but blocking stages like `$group` and `$sort` must buffer their whole input and are capped at 100 MB each.

Because each stage only sees the previous stage's output, order is both semantic and a performance decision: `$match` first can use an index and shrinks everything downstream, while the same `$match` at the end produces the same answer having done far more work. The most important structural fact is that `$group` destroys the document — after it, only `_id` and the accumulators you declared exist.

📖 [Aggregation Fundamentals](./05-aggregation-fundamentals.md)
</details>

<details>
<summary>**12. `$match` before vs after `$group`?**</summary>

Before `$group`, `$match` filters the source documents — SQL's `WHERE` — and if it's the first stage it can use an index. After `$group`, it filters the computed aggregates — SQL's `HAVING` — and can't use an index, because those values didn't exist until the group ran.

They answer different questions. "Average salary of employees earning over 50k, by department" filters first. "Departments whose average salary exceeds 50k" filters after. Those produce different numbers from the same data, and both are valid. Production pipelines usually want both: an early `$match` for date range and status, and a late one for the threshold.

📖 [Intermediate Q9](./09-intermediate-aggregation.md)
</details>

<details>
<summary>**13. Why is `$first` dangerous?**</summary>

Because it means "the value from whichever document arrived at the group first" — not "the earliest" and not "the best." Without a preceding `$sort` the incoming order is unspecified, so the result is arbitrary. Worse, it often looks correct on a small test data set and changes in production.

The idiom is always `$sort` then `$group` with `$first`, and the sort is load-bearing — deleting it doesn't cause an error, just wrong answers. On 5.2 and later, `$top` and `$topN` express the intent directly by sorting within the group, which removes the coupling entirely.

📖 [Advanced Q21](./10-advanced-aggregation.md)
</details>

<details>
<summary>**14. What happens to a document with an empty array during `$unwind`?**</summary>

It's dropped entirely — same for a missing field or an explicit null. `preserveNullAndEmptyArrays: true` keeps it, and the path field is then absent from the output.

But that creates a second trap that's the more interesting half of the answer. After a `$lookup` plus a preserving `$unwind`, a user with zero orders still produces one row, so `{ $sum: 1 }` counts that phantom and every order-less user reports exactly one order. You need a conditional count: `{ $sum: { $cond: [{ $ne: ["$orders", null] }, 1, 0] } }`. This is the most common `$lookup` bug I've seen in production.

📖 [Aggregation Fundamentals §3](./05-aggregation-fundamentals.md), [Advanced Q24](./10-advanced-aggregation.md)
</details>

<details>
<summary>**15. How does `$lookup` perform, and how do you make it fast?**</summary>

It behaves like a correlated subquery — roughly one query against the foreign collection per input document. So with 10,000 input documents you get 10,000 lookups.

Two levers. Reduce the input: `$match` and even `$group` *before* the lookup, never after. And make each lookup cheap: the `foreignField` must be indexed, or every one of them is a collection scan — that alone is often the difference between 40 milliseconds and 40 seconds.

Beyond that, prefer the `let` plus `pipeline` form so you can filter, sort, limit and project *inside* the join. The simple form pulls every matching document and lets you discard them afterwards; for a user with 50,000 orders of which three are delivered, that's 50,000 documents materialised to keep three.

And the honest senior answer: if a page needs four `$lookup`s, the schema is the actual problem.

📖 [Aggregation Fundamentals §3](./05-aggregation-fundamentals.md), [Advanced Q27](./10-advanced-aggregation.md)
</details>

<details>
<summary>**16. `$project` vs `$addFields`?**</summary>

`$project` is exclusive: it outputs only the fields you name, so it fully redefines the document's shape. `$addFields` — and its alias `$set` — is additive: it adds or overwrites the fields you name and passes everything else through.

Practically, use `$addFields` mid-pipeline for computed values and `$project` at the very end to shape the API response. Reaching for `$project` mid-pipeline and then discovering a later stage needs a field you dropped is a common self-inflicted wound.

📖 [Aggregation Fundamentals §3](./05-aggregation-fundamentals.md)
</details>

<details>
<summary>**17. How would you find the top 3 items per category?**</summary>

Three ways, and I'd pick based on version. On 5.2 and later, `$group` with `$topN` — it sorts within each group and says exactly what it means. Before that, the classic shape: `$group` to get per-category-per-item totals, `$sort` by category then value descending, a second `$group` that `$push`es into an array, then `$slice` the first 3 — where that middle sort is what gives `$push` its ordering and removing it silently returns three arbitrary items.

The third option is `$setWindowFields` partitioned by category with `$rank`, then `$match` on rank ≤ 3. That one has a real advantage: it handles ties the way you usually want, returning all items tied at the boundary rather than arbitrarily cutting.

📖 [Intermediate Q16](./09-intermediate-aggregation.md), [Advanced Q26](./10-advanced-aggregation.md)
</details>

<details>
<summary>**18. When would you use `$facet`?**</summary>

When you need several different summaries of the same input in one pass. The canonical case is a search results page needing both the total count and the current page — as two queries they cost two scans, two round trips, and can disagree if data changes in between.

Three things to know about the cost: the shared prefix before `$facet` runs once and is the only part that can use an index, so filters belong *before* it; the whole output is a single document subject to the 16 MB limit; and it's blocking, so nothing emits until every sub-pipeline finishes.

📖 [Stages Reference](./06-aggregation-stages.md), [Intermediate Q11](./09-intermediate-aggregation.md)
</details>

<details>
<summary>**19. `$unwind` + `$group` vs `$filter`/`$map`/`$reduce`?**</summary>

If the computation happens *within* one document — an order's cart total, counting an order's items, filtering an array for display — use the array operators. They keep the cardinality flat: three documents in, three out, no blocking stage, and an empty array yields 0 rather than dropping the document.

`$unwind` is genuinely required only when you need to aggregate *across* documents on the exploded elements — total quantity sold per product across all orders, where one product's total is assembled from many parent documents.

With 100,000 orders averaging five items, `$unwind` creates 500,000 intermediate documents and `$reduce` creates none, for the same answer.

📖 [Intermediate Q17](./09-intermediate-aggregation.md), [Advanced Q30](./10-advanced-aggregation.md)
</details>

## Round 4 — Data Modeling (the differentiator)

<details>
<summary>**20. Embed or reference?**</summary>

Embed when the child is bounded, has no independent identity, and is read together with the parent — that buys a single-round-trip read and atomic updates for free, since a single-document write is always atomic. Reference when the child set is unbounded, is queried on its own, or churns far faster than the parent is read.

Then the part people miss: selectively apply the extended reference pattern. Copy the two or three fields the read path actually displays — an author's name and avatar onto a post — back onto the parent, so the common query needs no join at all.

The sizing heuristic is one-to-few embed, one-to-many reference, one-to-squillions reference from the child and consider bucketing.

📖 [Data Modeling §2](./03-data-modeling.md)
</details>

<details>
<summary>**21. Isn't duplicating data bad?**</summary>

In a normalised relational model, yes, because joins are cheap there and a single source of truth is the goal. In MongoDB joins are the expensive operation and reads dominate, so duplicating fields that are read-heavy and change-light is a deliberate trade: faster reads, simpler queries, paid for with write-side fan-out and eventual consistency. You own that fan-out explicitly — usually with a change stream watching the source collection.

And some duplication isn't a cache at all. An order's line-item prices and shipping address must be a *historical snapshot* — if the restaurant raises its prices tomorrow, last week's invoice must not change. Recognising that distinction is the real answer.

📖 [Data Modeling §3](./03-data-modeling.md)
</details>

<details>
<summary>**22. How do you handle a schema migration with zero downtime?**</summary>

The schema versioning pattern. Add a `schemaVersion` field, teach the application to read every supported version, and migrate documents lazily as they're written, with a low-priority background job sweeping the tail.

No migration window, no downtime, and rollback is just deploying the previous application version — the data still reads, because old and new shapes coexist by design. That's genuinely different from the relational answer, where you'd need a migration script and usually a window.

📖 [Data Modeling §4](./03-data-modeling.md)
</details>

<details>
<summary>**23. Name the schema patterns you know.**</summary>

The six I use most: **extended reference** — duplicate a few hot fields to avoid a join. **Computed** — calculate on write and store, so the read is a field access instead of an aggregation over 40,000 reviews. **Bucket** — group many time-series readings into one document, cutting document count and index entries by the bucket factor. **Subset** — keep the hot slice embedded and the rest in another collection, so the working set stays cache-resident. **Schema versioning** — for zero-downtime migrations. **Outlier** — model for the common case and flag the exceptions, so one celebrity with 30 million followers doesn't force a worse schema on everyone.

The anti-patterns I look for in review: unbounded arrays, a collection per tenant, bloated documents, and case-insensitive regex queries that can't use an index.

📖 [Data Modeling §4 and §5](./03-data-modeling.md)
</details>

<details>
<summary>**24. Design a schema for [any system]. How do you start?**</summary>

I start by listing the access patterns, not the entities — the top five queries and roughly how often each runs. That's the input to every subsequent decision, because MongoDB modeling optimises for query shape rather than for normal form.

Then for each relationship I ask: is it bounded? Is it read with its parent? Does it churn faster than the parent is read? That gives me embed-or-reference. Then I identify which fields the hot read path displays from referenced collections and denormalise just those. Then I name the indexes each hot query needs and check their field order against ESR. Finally I sanity-check for the anti-patterns — anything that grows without bound, anything that would make a document large enough to hurt cache efficiency.

Saying "let me list the access patterns first" out loud is half the grade on this question.

📖 [Data Modeling §6](./03-data-modeling.md)
</details>

## Round 5 — Architecture & Operations

<details>
<summary>**25. How does MongoDB achieve high availability?**</summary>

Replica sets. Multiple `mongod` processes hold the same data, one primary takes writes, and secondaries replicate asynchronously by tailing the primary's oplog. Members heartbeat every two seconds, and if the primary is unreachable for ten seconds the secondaries hold a Raft-like election; the most up-to-date candidate that can win a strict majority becomes primary. End to end it's typically about twelve seconds, and drivers retry buffered writes automatically, so the application sees a latency spike rather than errors.

The minimum production topology is three nodes, not two — with two, losing one leaves a node that can't win a majority, so the set goes read-only.

📖 [Replication](./11-replication.md)
</details>

<details>
<summary>**26. Why must the oplog be idempotent?**</summary>

Because entries get applied more than once — during crash recovery, catch-up after a failover, and initial sync. MongoDB guarantees it by recording *resolved results* rather than operations: an `$inc` by one is stored as the literal resulting value, `$currentDate` as the resolved timestamp, and an `updateMany` as N separate single-document entries. Replaying any entry produces the same state.

If the oplog stored `$inc: 1`, a replay would double-count.

📖 [Replication §2](./11-replication.md)
</details>

<details>
<summary>**27. Is MongoDB CP or AP?**</summary>

CP by default, and tunable. During a network partition the minority side has no primary and refuses writes, preserving consistency at the cost of availability.

But the knobs are per-operation. With `w: 1` and `secondaryPreferred` reads you shift toward AP — writes acknowledge before replicating and reads may be stale. With `w: "majority"` and `readConcern: "majority"` you get strong, rollback-proof guarantees. So the accurate answer is "CP by default, with per-operation controls that let you trade toward availability where the data allows it."

📖 [Replication §7](./11-replication.md), [Transactions](./13-transactions-and-concerns.md)
</details>

<details>
<summary>**28. `w: 1` vs `w: "majority"`?**</summary>

`w: 1` acknowledges as soon as the primary has the write in memory. It's fast, but if that primary fails before replicating, the write is rolled back — it comes back as a file on disk, not as data.

`w: "majority"` waits until a majority of members have it, which guarantees survival through any election, because any node that can win must contain it. The cost is latency.

My policy is majority for anything with business meaning — orders, payments, user records — and `w: 1` for high-volume low-value writes like metrics and analytics events. And always set `wtimeout` with majority, or you block indefinitely when a majority is unavailable.

📖 [Transactions §1](./13-transactions-and-concerns.md)
</details>

<details>
<summary>**29. What makes a good shard key?**</summary>

High cardinality so the key space splits into many chunks; low frequency so no single value holds a disproportionate share; and non-monotonic growth so inserts don't all land on the shard owning the top of the range. On top of those three, the key should appear in your highest-frequency queries, so they're targeted to one shard instead of scatter-gathered across all of them.

`{ createdAt: 1 }` fails the third — every insert hits one shard. A raw ObjectId `_id` fails it for the same reason, since ObjectIds are timestamp-prefixed. Hashing fixes distribution but destroys range queries and sorting. A compound key like `{ userId: 1, createdAt: 1 }` usually satisfies all four: it's monotonic only *within* a user, so writes spread across the cluster, and "this user's recent orders" is targeted to one shard and comes back pre-sorted.

📖 [Sharding §3](./12-sharding.md)
</details>

<details>
<summary>**30. When should you shard?**</summary>

Later than most people think. Sharding adds routers, config servers, a balancer, cross-shard query semantics, and a key decision that's expensive to change.

Before it: add RAM so the working set fits in the WiredTiger cache — usually the single biggest win. Fix missing or badly ordered indexes. Fix schemas with bloated documents or unbounded arrays. Move analytics onto tagged secondaries. Archive cold data.

Shard when you genuinely exceed one machine: data beyond a practical single disk, write throughput beyond one primary, or a working set no single machine's RAM can hold. That middle one is the key point — replication cannot scale writes, since every secondary applies the same write load. Sharding is the only horizontal write-scaling mechanism MongoDB has.

📖 [Sharding §4](./12-sharding.md)
</details>

<details>
<summary>**31. Does MongoDB support transactions?**</summary>

Yes — multi-document ACID transactions since 4.0 on replica sets and 4.2 across shards, with snapshot isolation.

But the more useful answer is that a single-document write has *always* been atomic, however many fields and nested arrays it touches. So a well-designed schema — where data that changes together lives together — rarely needs one. And many cases that look transactional aren't: putting the precondition in the update filter, like `{ _id, stock: { $gte: 1 } }` with `$inc: { stock: -1 }`, gives you a race-free conditional decrement in a single atomic operation.

Transactions are right for genuinely separate entities, like moving money between two accounts. They cost you: a 60-second default limit, a 16 MB oplog entry cap, and lower throughput. And in code, use `withTransaction` rather than hand-rolling commit — it's what supplies the retry loop for transient conflicts.

📖 [Transactions §3](./13-transactions-and-concerns.md)
</details>

<details>
<summary>**32. What are change streams?**</summary>

A supported, resumable subscription to data changes, exposed as an aggregation pipeline you can filter. It's built on the oplog but gives you guarantees direct oplog tailing doesn't: a stable event format, cross-shard support, only majority-committed changes so you never react to data that gets rolled back, and a resume token so you restart exactly where you stopped after a crash.

They're the mechanism behind denormalisation fan-out, cache invalidation, syncing a search index, and real-time notifications. If I duplicate a user's display name onto their posts, a change stream on `users` is what keeps it in sync.

📖 [Transactions §5](./13-transactions-and-concerns.md)
</details>

## Round 6 — Node.js / MERN specific

<details>
<summary>**33. How do you configure connection pooling?**</summary>

Create exactly one `MongoClient` for the process lifetime and reuse it — the client *is* the pool. Creating one per request is the classic MERN bug and causes a connection storm under load.

Tune `maxPoolSize` against the server's connection limit divided by the number of app instances, keep a small `minPoolSize` warm, and always set `waitQueueTimeoutMS` and `serverSelectionTimeoutMS` so saturation surfaces as a fast error rather than an indefinite hang.

Serverless changes the math: every function instance holds its own pool, so 200 concurrent instances at `maxPoolSize: 10` is 2,000 connections. There you drop the pool size to a handful and cache the client in module scope so warm invocations reuse it.

📖 [Production Playbook §1](./14-production-playbook.md)
</details>

<details>
<summary>**34. Is NoSQL injection real?**</summary>

Yes — not string injection, but operator injection. If request data goes straight into a filter, posting `{"$ne": null}` as the password makes the query match any non-null value and bypasses authentication entirely.

The primary defence is type validation at the request boundary — Zod, Joi, whatever — so a field declared as a string can never arrive as an object. Secondarily, strip keys beginning with `$` from user-supplied objects. And never build `$where` or `$expr` from user input, since `$where` executes JavaScript server-side.

📖 [Production Playbook §2](./14-production-playbook.md)
</details>

<details>
<summary>**35. Mongoose or the native driver?**</summary>

Mongoose gives you schema declaration and validation in one place, middleware hooks, population, and automatic type casting — including casting an `_id` string to an ObjectId, which is why developers who only use Mongoose get caught the first time they touch the native driver.

The costs are a performance overhead, an abstraction that can hide what query actually runs, and lagging support for newer aggregation features. I'd use Mongoose on a team that benefits from enforced structure and conventions, and the native driver where I want full control of aggregation pipelines and predictable performance. A common middle ground is Mongoose for CRUD and the native collection handle for heavy pipelines.

Either way, schema validation belongs in the database too — Mongoose validation doesn't protect against writes from any other client.
</details>

<details>
<summary>**36. How do you paginate efficiently?**</summary>

Not with `skip`. `skip(n)` makes the server walk and discard n documents, so cost grows linearly with page depth and deep pages become unusable.

Range-based pagination instead: sort by an indexed, unique key and filter on the last value from the previous page — `{ _id: { $lt: lastSeenId } }` with a limit. Constant cost per page, and it's also immune to the duplicate-and-skipped-row problem you get when data changes between page loads.

If the UI needs a total count as well, `$facet` gets both from one scan. And whatever the sort key, add a unique tiebreaker — otherwise ties order non-deterministically and rows drift between pages.

📖 [Production Playbook §6](./14-production-playbook.md)
</details>

<details>
<summary>**37. How would you build a job queue on MongoDB?**</summary>

`findOneAndUpdate` with a filter of `{ status: "QUEUED" }`, an update setting `status: "PROCESSING"` plus a worker ID and a claim timestamp, `sort` by priority and age, and `returnDocument: "after"`. Because it's atomic on a single document, N workers polling concurrently can never claim the same job — no locks, no transaction.

Then a sweeper resets `PROCESSING` jobs whose `claimedAt` is older than the visibility timeout, which handles worker crashes. Index on `{ status: 1, priority: -1, createdAt: 1 }` so the claim is a targeted index scan.

📖 [CRUD §3](./02-crud-deep-dive.md)
</details>

<details>
<summary>**38. How do you serve an expensive analytics query at page-load latency?**</summary>

Precompute it. Run the heavy aggregation on a schedule and write results into a summary collection with `$merge`, which updates incrementally rather than rebuilding — MongoDB calls this an on-demand materialised view. The dashboard then serves a plain indexed `find()`.

If the numbers need to be closer to real time, maintain them incrementally at write time using the computed pattern — storing `ratingSum`, `ratingCount` and `ratingAvg` on the product rather than aggregating 40,000 reviews per page view — or drive the updates from a change stream.

📖 [Stages Reference](./06-aggregation-stages.md), [Production Playbook §6](./14-production-playbook.md)
</details>

## The five sentences worth memorising verbatim

1. **"Data that is accessed together should be stored together."** — the whole of MongoDB modeling.
2. **"`$group` destroys the document."** — explains most aggregation confusion.
3. **"Equality, Sort, Range."** — compound index field order.
4. **"`$first` means *whichever arrived first*, so `$sort` is load-bearing."**
5. **"Replication is for availability; sharding is for scale. Replication cannot scale writes."**

## Questions to ask *them*

Asking good questions is part of the interview.

- What does your schema look like for the highest-traffic collection, and how did you arrive at it?
- Are you sharded? What's the shard key, and would you pick it again?
- Where do you sit on the write concern spectrum, and was that a deliberate decision?
- How do you keep denormalised data in sync — change streams, background jobs, or accepted staleness?
- What's the last MongoDB-related incident you had?

That last one tells you more about the engineering culture than anything on the job description.
