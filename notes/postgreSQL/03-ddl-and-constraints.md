# DDL, Constraints & Schemas

> **What you will be able to do after this page**
>
> - Write a production-grade `CREATE TABLE` with the right key strategy and every constraint that belongs there.
> - Explain why PostgreSQL DDL is transactional and what that buys you in a migration.
> - Run schema changes on a live table without locking it — and know exactly which `ALTER TABLE` forms rewrite.
> - Use schemas, `search_path`, generated columns, and identity columns correctly.

---

## 1. A table, properly built

```sql
CREATE TABLE orders (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id    uuid        NOT NULL DEFAULT gen_random_uuid() UNIQUE,
    customer_id  bigint      NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
    status       order_status NOT NULL DEFAULT 'pending',
    subtotal     numeric(12,2) NOT NULL CHECK (subtotal >= 0),
    tax          numeric(12,2) NOT NULL DEFAULT 0 CHECK (tax >= 0),
    total        numeric(12,2) GENERATED ALWAYS AS (subtotal + tax) STORED,
    metadata     jsonb       NOT NULL DEFAULT '{}'::jsonb,
    placed_at    timestamptz NOT NULL DEFAULT now(),
    shipped_at   timestamptz,
    CONSTRAINT shipped_after_placed CHECK (shipped_at IS NULL OR shipped_at >= placed_at)
);
```

Every line of that is a decision. Let's take them apart.

## 2. Auto-incrementing keys: `serial` vs `IDENTITY`

```sql
-- Legacy (still everywhere, still works)
id serial PRIMARY KEY          -- integer, expands to a sequence + DEFAULT nextval(...)
id bigserial PRIMARY KEY       -- bigint version

-- Modern, SQL-standard (PG 10+) — prefer this
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

What `serial` actually is — it's not a type:

```sql
CREATE TABLE t (id serial);
-- is exactly equivalent to:
CREATE SEQUENCE t_id_seq;
CREATE TABLE t (id integer NOT NULL DEFAULT nextval('t_id_seq'));
ALTER SEQUENCE t_id_seq OWNED BY t.id;
```

| | `serial` | `GENERATED ... AS IDENTITY` |
| :--- | :--- | :--- |
| Standard SQL | ❌ Postgres-ism | ✅ |
| Sequence ownership | Attached, but the column's default can be dropped | Truly owned by the column |
| Can you insert an explicit value? | Yes, always (and desync the sequence) | `ALWAYS` → no (unless `OVERRIDING SYSTEM VALUE`); `BY DEFAULT` → yes |
| Permission model | Needs `USAGE` on the sequence granted separately | Handled with the table |

**Use `GENERATED ALWAYS AS IDENTITY` for new work.** `ALWAYS` prevents the classic bug where a data import inserts explicit IDs, the sequence is never advanced, and six months later inserts start failing with duplicate key errors.

If that has already happened to you:

```sql
SELECT setval(pg_get_serial_sequence('orders','id'),
              (SELECT max(id) FROM orders));
```

### Sequences are non-transactional on purpose

```sql
BEGIN;
INSERT INTO t DEFAULT VALUES;   -- id = 5
ROLLBACK;
INSERT INTO t DEFAULT VALUES;   -- id = 6, NOT 5 — the 5 is burned forever
```

`nextval()` never rolls back, because rolling it back would force every concurrent inserter to serialise. **Gaps in an ID sequence are normal and expected.** If you need gapless numbering (invoice numbers in some jurisdictions), you need an explicit counter table with row locking — and you accept the serialisation.

Sequences also cache: `CACHE 50` makes each backend grab 50 values at once, which is faster but produces bigger gaps and out-of-order IDs across sessions.

:::info[PostgreSQL vs MySQL]
| PostgreSQL | MySQL |
| :--- | :--- |
| `GENERATED ALWAYS AS IDENTITY` / `serial`, backed by a **standalone sequence object** | `AUTO_INCREMENT` column attribute, counter stored **in the table** |
| Many sequences per table possible; a sequence can be shared across tables | **One `AUTO_INCREMENT` column per table**, must be indexed |
| `nextval()` is callable directly, usable anywhere | No user-callable "next value" |
| Get the value back with `RETURNING id` — works for multi-row inserts | `LAST_INSERT_ID()` — returns only the **first** ID of a multi-row insert |
| Sequence value survives restart exactly | Pre-8.0 InnoDB recomputed the counter as `max(id)+1` on restart, so deleted-then-restarted tables reused IDs. Fixed in 8.0 (persisted to the redo log) |
| No `AUTO_INCREMENT` gaps concept — gaps are normal | Gaps also occur (rollbacks, `innodb_autoinc_lock_mode=2`) but people expect them less |

**`RETURNING` vs `LAST_INSERT_ID()` is the practically important one:** on Postgres, `INSERT ... RETURNING id, public_id, placed_at` gets you the whole generated row in one round trip, for any number of rows. MySQL needs a second query.
:::

## 3. Constraints

### `NOT NULL`

Cheapest, most valuable constraint there is. Default to it, and require an argument to leave it off.

### `CHECK`

```sql
ALTER TABLE orders ADD CONSTRAINT positive_total CHECK (total >= 0);
```

A `CHECK` passes if the expression is `true` **or `NULL`**. So `CHECK (age > 18)` allows `age IS NULL`. That's SQL-standard three-valued logic and it surprises everyone once.

Adding a `CHECK` to a big live table takes an `ACCESS EXCLUSIVE` lock while it validates every row. Do it in two steps:

```sql
ALTER TABLE orders ADD CONSTRAINT positive_total CHECK (total >= 0) NOT VALID;  -- instant, brief lock
ALTER TABLE orders VALIDATE CONSTRAINT positive_total;                          -- slow, but only SHARE UPDATE EXCLUSIVE
```

`NOT VALID` means "enforce for new and modified rows, don't check existing ones yet." This two-step pattern is the standard safe-migration technique and worth naming in an interview.

:::info[PostgreSQL vs MySQL]
`CHECK` constraints were **parsed and ignored** by MySQL until **8.0.16**. Any schema written for MySQL 5.7 with `CHECK` constraints in it was silently unenforced. In MySQL 8.0.16+ they work. Postgres has always enforced them, and additionally supports the `NOT VALID` / `VALIDATE` split, which MySQL lacks.
:::

### `UNIQUE`

A `UNIQUE` constraint is implemented as a unique index. In Postgres, **NULLs are distinct** by default, so multiple rows may have `NULL` in a unique column:

```sql
CREATE TABLE u (email text UNIQUE);
INSERT INTO u VALUES (NULL), (NULL);   -- both succeed
```

PG 15+ can change this:

```sql
CREATE TABLE u (email text UNIQUE NULLS NOT DISTINCT);  -- now only one NULL allowed
```

**Partial unique indexes** are a Postgres superpower — a unique constraint that applies only to some rows:

```sql
-- Only one active subscription per user, but any number of cancelled ones
CREATE UNIQUE INDEX one_active_sub
  ON subscriptions (user_id)
  WHERE status = 'active';

-- Soft deletes: email unique only among non-deleted rows
CREATE UNIQUE INDEX users_email_live
  ON users (lower(email))
  WHERE deleted_at IS NULL;
```

:::info[PostgreSQL vs MySQL]
| PostgreSQL | MySQL |
| :--- | :--- |
| **Partial indexes** (`WHERE ...`) — full support | **No partial indexes.** Workaround: a generated column that is `NULL` when the condition is false, then a unique index on it |
| **Expression indexes** (`lower(email)`) | Functional indexes since **8.0.13** — `CREATE INDEX ((LOWER(email))))`, and generated-column workarounds before that |
| NULLs distinct by default; `NULLS NOT DISTINCT` available in 15+ | NULLs distinct, **no option to change it** |

The `WHERE deleted_at IS NULL` unique index is one of the most immediately useful things Postgres has that MySQL doesn't — soft deletes plus uniqueness is genuinely awkward on MySQL.
:::

### Foreign keys

```sql
customer_id bigint NOT NULL REFERENCES customers(id)
    ON DELETE RESTRICT
    ON UPDATE CASCADE
    DEFERRABLE INITIALLY IMMEDIATE
```

| Action | Effect on delete of parent |
| :--- | :--- |
| `NO ACTION` (default) | Error — but **checked at end of statement**, so deferrable |
| `RESTRICT` | Error — checked immediately, **cannot be deferred** |
| `CASCADE` | Delete the children too |
| `SET NULL` | Null out the child column |
| `SET DEFAULT` | Set the child column to its default |

PG 15+ allows column-specific `SET NULL (col)` for composite FKs.

**Deferrable constraints** — Postgres can postpone FK checking to `COMMIT`:

```sql
ALTER TABLE orders
  ADD CONSTRAINT fk_cust FOREIGN KEY (customer_id) REFERENCES customers(id)
  DEFERRABLE INITIALLY DEFERRED;

BEGIN;
  INSERT INTO orders (customer_id, ...) VALUES (999, ...);  -- customer 999 doesn't exist yet — OK for now
  INSERT INTO customers (id, ...) VALUES (999, ...);
COMMIT;                                                     -- checked here, passes
```

This makes circular references and bulk loads in arbitrary order possible.

:::warning[Always index your foreign keys]
Postgres automatically indexes the **referenced** (parent) column — it must be unique — but **not the referencing (child) column**. Without that index, every `DELETE` or key `UPDATE` on the parent does a **sequential scan of the child table** to check for references. On a big child table this is the difference between 1 ms and 30 seconds, and it's a top cause of mysterious delete-related lock pileups.

```sql
-- find unindexed FKs
SELECT c.conrelid::regclass AS child, a.attname
FROM pg_constraint c
JOIN unnest(c.conkey) WITH ORDINALITY k(attnum, ord) ON true
JOIN pg_attribute a ON a.attrelid = c.conrelid AND a.attnum = k.attnum
WHERE c.contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index i
    WHERE i.indrelid = c.conrelid AND (i.indkey::int2[])[0] = k.attnum
  );
```
:::

:::info[PostgreSQL vs MySQL]
| PostgreSQL | MySQL (InnoDB) |
| :--- | :--- |
| Does **not** auto-create an index on the child column | **Automatically creates** an index on the child column if one doesn't exist |
| `DEFERRABLE` FKs — check at COMMIT | **No deferrable constraints.** Workaround: `SET FOREIGN_KEY_CHECKS = 0` (session-wide, unsafe) |
| MyISAM irrelevant — FKs always enforced | FKs are InnoDB-only; MyISAM silently ignores them |
| FK checked per statement | Same |

MySQL's auto-index is genuinely friendlier here. Postgres' deferrable constraints are genuinely more powerful. Know both, because both come up.
:::

### Exclusion constraints (Postgres only)

Covered in [Data Types §9](./02-data-types.md) — `EXCLUDE USING GIST (room_id WITH =, during WITH &&)` prevents overlapping bookings declaratively. No MySQL equivalent.

## 4. Generated columns

```sql
total numeric(12,2) GENERATED ALWAYS AS (subtotal + tax) STORED
```

Computed from other columns in the same row, maintained by the engine, indexable.

```sql
-- Extremely common: index a JSON path via a generated column
ALTER TABLE events
  ADD COLUMN event_type text GENERATED ALWAYS AS (payload ->> 'type') STORED;
CREATE INDEX ON events (event_type);
```

Rules: the expression must be **immutable**, reference only columns of the same row, and cannot reference other generated columns or use subqueries.

:::info[PostgreSQL vs MySQL]
| PostgreSQL | MySQL 5.7+ |
| :--- | :--- |
| `STORED` only (through PG 17); **`VIRTUAL` generated columns added in PG 18** | Both `VIRTUAL` (default, computed on read) and `STORED` |
| Indexable when `STORED` | Both indexable; virtual columns get a "virtual index" |
| Not needed for JSON indexing — you can GIN-index `jsonb` directly | **The primary way to index JSON** on MySQL |

MySQL had the better generated-column story for years; PG 18 closes it. But Postgres needed it less, because you can index a `jsonb` column and an arbitrary expression directly.
:::

An alternative Postgres has and MySQL doesn't: an **expression index**, which gives you index-ability without adding a column at all:

```sql
CREATE INDEX ON events ((payload ->> 'type'));
CREATE INDEX ON users (lower(email));
```

## 5. Schemas and `search_path`

A **schema** is a namespace inside a database.

```sql
CREATE SCHEMA billing;
CREATE TABLE billing.invoices (...);
SELECT * FROM billing.invoices;
```

`search_path` decides what an unqualified name resolves to:

```sql
SHOW search_path;                       -- "$user", public
SET search_path TO billing, public;
SELECT * FROM invoices;                 -- resolves to billing.invoices
```

Uses:

- **Multi-tenancy** — one schema per tenant, identical tables, `search_path` set at connection time. Works well into the low thousands of tenants; beyond that catalog bloat and migration time hurt.
- **Logical grouping** — `auth`, `billing`, `analytics` in one database, joinable in one query.
- **Extensions** — `CREATE EXTENSION ... SCHEMA extensions;` keeps them out of `public`.

:::danger[`search_path` is a security surface]
A `SECURITY DEFINER` function that calls an unqualified `lower(x)` can be hijacked by a user who creates their own `lower()` in a schema earlier in the path. Always pin it:
```sql
CREATE FUNCTION f() RETURNS void
LANGUAGE plpgsql SECURITY DEFINER
SET search_path = pg_catalog, pg_temp    -- ← mandatory
AS $$ ... $$;
```
Also note: since **PG 15**, `CREATE` on `public` is no longer granted to `PUBLIC` by default — a good change that breaks old scripts.
:::

:::info[PostgreSQL vs MySQL]
| PostgreSQL | MySQL |
| :--- | :--- |
| `database` → `schema` → `table` | `database` **is** `schema` (aliases) → `table` |
| One connection = one database; **cannot** join across databases | `USE db1;` then `SELECT ... FROM db2.t` — cross-database joins are free |
| Cross-database needs `postgres_fdw` or `dblink` | Native |
| `search_path` for name resolution | `USE`, plus explicit `db.table` |

**Porting rule: a MySQL database becomes a PostgreSQL schema.** If a MySQL app joins across `app_db` and `analytics_db`, on Postgres those become two schemas in one database, and the joins keep working.
:::

## 6. Transactional DDL — a genuine Postgres advantage

```sql
BEGIN;
  ALTER TABLE orders ADD COLUMN discount numeric(12,2);
  UPDATE orders SET discount = 0;
  ALTER TABLE orders ALTER COLUMN discount SET NOT NULL;
  CREATE INDEX idx_orders_discount ON orders (discount);
  -- something goes wrong
ROLLBACK;      -- ← the table is EXACTLY as it was. No half-applied migration.
```

In PostgreSQL, nearly all DDL is transactional: `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `CREATE INDEX`, even `CREATE TYPE`. A failed migration leaves nothing behind.

The exceptions (cannot run inside a transaction block):

- `CREATE INDEX CONCURRENTLY` / `DROP INDEX CONCURRENTLY`
- `VACUUM`, `ANALYZE`
- `CREATE DATABASE`, `DROP DATABASE`, `ALTER SYSTEM`
- `REINDEX CONCURRENTLY`
- `ALTER TYPE ... ADD VALUE` (allowed in a transaction since PG 12, but the new value can't be *used* in the same transaction)

:::info[PostgreSQL vs MySQL]
| PostgreSQL | MySQL |
| :--- | :--- |
| DDL is **transactional and rollback-safe** | DDL causes an **implicit COMMIT** before and after. There is no rolling back a migration |
| A failed multi-statement migration leaves zero changes | A failed migration leaves you half-migrated, at 3am, manually reconstructing state |
| Migration tools wrap each migration in a transaction | Tools must implement `down` migrations and hope |

This is one of the strongest concrete arguments for PostgreSQL, and it's the answer to "give me a real reason to prefer Postgres" that isn't hand-waving. MySQL 8.0 added *atomic* DDL (a single DDL statement won't leave a partial state after a crash), which is a real improvement — but it still cannot be grouped in a user transaction with DML.
:::

## 7. `ALTER TABLE` — what locks, what rewrites

This is the operational knowledge that separates people who have run Postgres in production from people who haven't.

| Operation | Lock | Rewrites table? |
| :--- | :--- | :--- |
| `ADD COLUMN` (nullable, no default) | ACCESS EXCLUSIVE, **instant** | No |
| `ADD COLUMN ... DEFAULT <constant>` | ACCESS EXCLUSIVE, **instant since PG 11** | No (stored in catalog) |
| `ADD COLUMN ... DEFAULT <volatile>` e.g. `gen_random_uuid()` | ACCESS EXCLUSIVE | **YES — full rewrite** |
| `DROP COLUMN` | ACCESS EXCLUSIVE, instant | No (marked dead, space reclaimed by later rewrite) |
| `ALTER COLUMN TYPE` (e.g. `int` → `bigint`) | ACCESS EXCLUSIVE | **YES — full rewrite + all indexes** |
| `ALTER COLUMN TYPE varchar(50)` → `varchar(100)` | ACCESS EXCLUSIVE, instant | No (binary-coercible widening) |
| `SET NOT NULL` | ACCESS EXCLUSIVE | No, but **full scan to verify** |
| `ADD CHECK ... NOT VALID` | ACCESS EXCLUSIVE, instant | No |
| `VALIDATE CONSTRAINT` | SHARE UPDATE EXCLUSIVE | No — **doesn't block reads or writes** |
| `CREATE INDEX` | SHARE (blocks writes) | No |
| `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE | No — **doesn't block writes** |
| `SET DEFAULT` / `DROP DEFAULT` | ACCESS EXCLUSIVE, instant | No |
| `RENAME COLUMN` / `RENAME TABLE` | ACCESS EXCLUSIVE, instant | No |

:::danger[ACCESS EXCLUSIVE + a lock queue = an outage]
Even an *instant* ACCESS EXCLUSIVE lock is dangerous. If a long-running `SELECT` is holding an ACCESS SHARE lock, your `ALTER` waits — and **every query that arrives after it also waits**, because lock requests queue in order. A one-millisecond DDL becomes a full site outage behind one slow report.

Always guard DDL:
```sql
SET lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN note text;   -- fails fast rather than queueing
```
Retry in a loop. This single setting prevents most DDL-induced incidents.
:::

### `CREATE INDEX CONCURRENTLY`

```sql
CREATE INDEX CONCURRENTLY idx_orders_placed ON orders (placed_at DESC);
```

Builds in two passes so writes continue throughout. The costs: it takes roughly twice as long, cannot run inside a transaction block, and **if it fails it leaves an `INVALID` index behind** that you must drop manually:

```sql
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
DROP INDEX CONCURRENTLY idx_orders_placed;
```

:::info[PostgreSQL vs MySQL]
| PostgreSQL | MySQL 8 (InnoDB) |
| :--- | :--- |
| `CREATE INDEX CONCURRENTLY` — online, no writes blocked | `ALTER TABLE ... ADD INDEX, ALGORITHM=INPLACE, LOCK=NONE` — also online |
| `ADD COLUMN` with a constant default is instant (PG 11+) | `ALGORITHM=INSTANT` for adding a column at the **end** of the table (8.0.12+) |
| Column type widening `varchar(50)→varchar(100)` is metadata-only | Also metadata-only if it stays within the same length-byte class |
| No built-in online table rewrite → use **pg_repack** | `pt-online-schema-change` / `gh-ost` are the community standard |

Both ecosystems solved the same problem with external tools. Neither is meaningfully ahead here in 2026; the difference is that Postgres lets you wrap the whole migration in a transaction.
:::

### The safe "add a NOT NULL column with a default" recipe

```sql
-- PG 11+ with a CONSTANT default: this is already instant.
ALTER TABLE orders ADD COLUMN currency text NOT NULL DEFAULT 'INR';

-- With a VOLATILE default (uuid, now()), do it in stages instead:
ALTER TABLE orders ADD COLUMN public_id uuid;                       -- instant
UPDATE orders SET public_id = gen_random_uuid()
  WHERE public_id IS NULL AND id BETWEEN 1 AND 100000;              -- batched
ALTER TABLE orders ADD CONSTRAINT public_id_nn
  CHECK (public_id IS NOT NULL) NOT VALID;                          -- instant
ALTER TABLE orders VALIDATE CONSTRAINT public_id_nn;                -- non-blocking scan
ALTER TABLE orders ALTER COLUMN public_id SET NOT NULL;             -- instant in PG 12+,
                                                                    -- since the CHECK proves it
ALTER TABLE orders DROP CONSTRAINT public_id_nn;
```

That last trick — a validated `CHECK (col IS NOT NULL)` letting `SET NOT NULL` skip its scan — is a PG 12+ feature and a great thing to know off the top of your head.

## 8. Views and materialized views

```sql
CREATE VIEW active_orders AS
  SELECT * FROM orders WHERE status <> 'cancelled';

CREATE MATERIALIZED VIEW daily_revenue AS
  SELECT date_trunc('day', placed_at) AS day, sum(total) AS revenue
  FROM orders GROUP BY 1;

CREATE UNIQUE INDEX ON daily_revenue (day);      -- required for CONCURRENTLY
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;
```

A view is a stored query, re-executed each time and inlined into the calling query's plan. A **materialized view** stores the result physically and must be refreshed. `REFRESH ... CONCURRENTLY` keeps the view readable during the refresh but requires a unique index and is slower.

Views are **updatable** automatically if they're simple (one table, no aggregates/DISTINCT/GROUP BY). Otherwise use an `INSTEAD OF` trigger.

:::info[PostgreSQL vs MySQL]
| PostgreSQL | MySQL |
| :--- | :--- |
| Views + **materialized views** with `REFRESH CONCURRENTLY` | Views only. **No materialized views** — you build a summary table and refresh it yourself |
| Views can be `SECURITY INVOKER` (default) or `SECURITY DEFINER`-ish via `security_barrier`, and PG 15+ `security_invoker` on the view | `SQL SECURITY DEFINER` / `INVOKER` on views |
| Complex views are inlined and optimised into the outer query | Historically materialised into a temp table (`derived_merge` improved this in 5.7+) |
:::

## 9. Comments and introspection

```sql
COMMENT ON TABLE orders IS 'Customer orders. One row per checkout.';
COMMENT ON COLUMN orders.total IS 'subtotal + tax, generated';

\d+ orders                       -- psql: full description
SELECT * FROM information_schema.columns WHERE table_name = 'orders';
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
 WHERE conrelid = 'orders'::regclass;
SELECT indexdef FROM pg_indexes WHERE tablename = 'orders';
```

`pg_get_constraintdef` and `pg_get_indexdef` reconstruct the exact DDL — invaluable when comparing environments.

## 10. Rapid-fire recall

<details>
<summary>**`serial` or `IDENTITY`?**</summary>

`IDENTITY` for new work. `serial` isn't a real type — it's shorthand that creates a sequence and a column default, it's non-standard, and it lets anyone insert an explicit ID without advancing the sequence, which eventually causes duplicate-key errors on a table that used to work. `GENERATED ALWAYS AS IDENTITY` is standard SQL, owned properly by the column, and refuses explicit values unless you say `OVERRIDING SYSTEM VALUE`. Use `bigint` either way.
</details>

<details>
<summary>**Why are there gaps in my ID sequence?**</summary>

Because `nextval()` is deliberately non-transactional — it doesn't roll back. If it did, every concurrent inserter would have to serialise on the sequence. So a rolled-back transaction burns its ID permanently, and sequence caching (`CACHE n`) creates larger gaps per backend. Gaps are correct behaviour; if you need gapless numbering you need a counter table with row-level locking and you accept the serialisation cost.
</details>

<details>
<summary>**What does transactional DDL give you?**</summary>

The ability to wrap a whole migration — several `ALTER TABLE`s, a backfill `UPDATE`, an index creation — in one transaction, so that a failure anywhere rolls the schema back to exactly where it started. There is no half-applied migration state to reason about at 3am. MySQL commits implicitly around every DDL statement, so this simply isn't available there; MySQL 8's atomic DDL guarantees a single statement is all-or-nothing after a crash, but you still can't group statements.
</details>

<details>
<summary>**How do you add a column to a 500-million-row table safely?**</summary>

If it's nullable, or has a *constant* default, `ALTER TABLE ... ADD COLUMN` is a catalog-only change and instant since PG 11 — but I'd still set `lock_timeout` first, because the ACCESS EXCLUSIVE lock queues behind any long-running query and every subsequent query queues behind that. If the default is volatile, like `gen_random_uuid()`, that rewrites the entire table, so instead I add the column nullable, backfill in batches with sleeps, add a `CHECK (col IS NOT NULL) NOT VALID`, `VALIDATE` it without blocking writes, then `SET NOT NULL` — which in PG 12+ is instant because the validated check proves it.
</details>

<details>
<summary>**Does PostgreSQL index foreign keys automatically?**</summary>

No — only the referenced parent column, which must be unique anyway. The child column gets no index, and without one every parent delete or key update sequentially scans the child table to check for references. MySQL *does* auto-create it. So on Postgres, indexing FK columns is an explicit step you must remember, and forgetting it is one of the most common causes of surprisingly slow deletes and lock pileups.
</details>

<details>
<summary>**What's a partial index and when do you use it?**</summary>

An index with a `WHERE` clause, so it only contains rows matching the predicate. It's smaller, faster to scan, and cheaper to maintain. The two killer uses are a partial *unique* index — "only one active subscription per user" or "email unique among non-soft-deleted rows" — and indexing a rare status value in a huge table, like `WHERE status = 'pending'` on a job queue where 99.9% of rows are done. MySQL has no partial indexes at all, which makes soft-delete uniqueness genuinely awkward there.
</details>

<details>
<summary>**What does `NOT VALID` do on a constraint?**</summary>

It adds the constraint so it's enforced for all new and updated rows, but skips validating the existing rows — so it takes only a brief lock instead of scanning the table. You then run `VALIDATE CONSTRAINT` separately, which does the full scan under a `SHARE UPDATE EXCLUSIVE` lock that doesn't block reads or writes. It's the standard way to add a `CHECK` or foreign key to a large live table.
</details>

<details>
<summary>**Schema vs database in PostgreSQL?**</summary>

A cluster contains databases, a database contains schemas, a schema contains tables. You connect to exactly one database and cannot join across databases without a foreign data wrapper. In MySQL, "schema" and "database" are synonyms — there are only two levels — and cross-database joins are free. So when porting, a MySQL database becomes a PostgreSQL *schema*, not a PostgreSQL database, and the joins keep working.
</details>
